# 上下文管理器 v1.4 计划修订

## 摘要

仅调整 `static/plan/v1.4-context-manager.md`，本轮不修改代码。

v1.4 采用单机实例、硬上限和失败关闭策略：

- 应用侧绝对输入上限：`256,000 tokens`。
- 估算安全发送上限：`95% × 256,000 = 243,200 tokens`。
- Prompt usage 达到 `80%`，即 `204,800 tokens` 时，在下一次请求 LLM 前压缩。
- 压缩后只保留最近一轮完整问答。
- 最近一轮之前的所有成功对话，与已有摘要合并为一个新摘要。
- 压缩目标是尽量将最终 Prompt 降到 `256k` 的 `5%～20%`，即约 `12,800～51,200 tokens`；这是软目标，低于 5% 不算失败。
- 摘要使用与主请求相同的模型，但不使用 Memory、Tool 或当前会话 Advisor。
- 摘要失败时不进入主模型请求，直接返回失败。
- 主模型返回非空最终结果后，立即将上下文、完整历史和引用元数据刷盘。
- 数据库刷盘失败时回滚本轮状态并返回失败。
- v1.4 只保证单 JVM 内的会话锁和并发安全。

## 请求与压缩流程

```text
加载会话并取得会话锁
  -> 组装完整当前 Prompt
  -> 估算最终 Prompt usage
  -> usage < 204800：不压缩
  -> usage >= 204800：保存压缩前快照
  -> 保留最近一轮完整问答
  -> 将更早的成功轮次与已有摘要合并生成一个新摘要
  -> 重新估算 system、摘要、最近一轮、当前 Prompt、XML、Tool definitions 和格式开销
  -> 预计 usage > 243200：返回上下文过大，不请求主模型
  -> 预计 usage <= 243200：请求主模型
  -> 主模型返回非空最终结果
  -> 更新 messages、history_messages、referenced_file_contents
  -> 立即同步刷盘
  -> 刷盘成功后返回回答
```

压缩发生在下一次主模型请求前，不在上一轮成功回答后立即执行。

如果当前没有可被压缩的旧轮次，则压缩视为 no-op；重新估算后仍必须满足安全发送上限。

## 上下文和摘要规则

`messages` 保存当前 LLM 上下文：

```json
[
  {
    "kind": "context_summary",
    "role": "system",
    "version": 1,
    "content": "历史对话摘要……"
  },
  {
    "role": "user",
    "content": "最近一轮问题"
  },
  {
    "role": "assistant",
    "content": "最近一轮回答"
  }
]
```

摘要生成规则：

- 摘要输入包括已有摘要和本次被移出的所有旧成功轮次。
- 当前用户 Prompt 不进入摘要。
- 摘要最多输出 `4,096 tokens`。
- 摘要必须保留用户目标、关键约束、已确认决策、重要事实和未完成事项。
- 摘要作为数据注入，不应被视为用户可控制的系统指令。
- 摘要生成失败、返回空内容或超过输出上限，都视为压缩失败。
- 压缩失败时恢复压缩前快照，不发送主模型请求。

Token 估算继续使用可替换的 `TokenCountEstimator`，初版使用 `JTokkitTokenCountEstimator`。实际 `promptTokens` 仅用于观测和后续校准，不替代请求前估算。

## 历史、引用与持久化

新增：

```sql
history_messages JSON NOT NULL DEFAULT (JSON_ARRAY())
```

`history_messages` 保存所有成功请求的原始用户问题和最终 assistant 回答：

- 不保存扩展 Prompt、选区 XML、Tool Call、Tool Response、Operations 或内部推理。
- 只有主模型返回非空最终结果后才追加。
- 主模型失败、压缩失败或刷盘失败均不得留下本轮历史。

`referenced_file_contents` 改为全量保存：

- 去除现有按最近 10 轮裁剪的逻辑。
- 继续沿用现有 JSON 结构和追加时机。
- 每次成功轮次与 `messages`、`history_messages` 一起同步刷盘。
- `clear()` 对引用元数据的行为保持当前实现不变。
- v1.4 暂不处理引用历史的分页、容量优化和淘汰。

刷盘策略：

- 主模型返回成功结果后，在会话锁内同步调用快照更新。
- 快照同时更新 `messages`、`history_messages` 和 `referenced_file_contents`。
- 更新失败时恢复本轮开始前的上下文、摘要、历史和引用状态，并返回持久化失败。
- 定时刷新保留为异常恢复和其他 dirty 状态的兜底机制。
- 只考虑单机单 JVM，不增加分布式锁、版本号或多实例冲突解决。

## 迁移、接口与兼容性

迁移需要：

- 更新 `ChatSession`、`ChatSessionMapper` 和 `static/init.sql`。
- 新增迁移脚本添加 `history_messages` 及 JSON 数组约束。
- 将现有 `messages` 中可识别的 `user` / `assistant` 消息复制到 `history_messages`。
- 已被旧版本滑动窗口裁剪的历史无法恢复。
- v1.4 不为损坏消息自动修复。

接口保持不变：

```http
GET /api/sessions/{sessionKey}
```

响应字段 `messages` 改为读取 `history_messages`，返回完整成功聊天历史；隐藏摘要和当前 LLM 上下文不返回前端。

错误行为至少区分：

- 上下文超过安全发送上限：上下文过大错误，不发送主模型请求。
- 摘要生成失败：上下文压缩失败，不发送主模型请求。
- 主模型失败：沿用当前模型失败处理。
- 同步刷盘失败：本轮状态回滚并返回持久化失败。

## 消息损坏处理

消息损坏恢复不在 v1.4 实现，文档中标记为已知缺陷和后续优化项：

- 当前 `messages` 或 `history_messages` 无法解析时，不静默丢弃或伪造数据。
- v1.4 直接返回会话加载失败。
- 后续版本再考虑从最近 10 条可解析历史消息生成新摘要，替换损坏的当前上下文。

## 测试与验收

重点验证：

- `204,799` tokens 不触发压缩，`204,800` tokens 在主模型调用前触发压缩。
- 压缩后只保留一个摘要和最近一轮完整问答。
- 多次压缩始终合并为一个摘要。
- 预计 Prompt 超过 `243,200` 时不会发送主模型请求。
- 摘要调用使用相同模型，但不会递归进入 Memory 或 Tool。
- 摘要失败时主模型不被调用，且压缩前状态保持不变。
- 主模型返回非空结果后立即执行数据库更新。
- 数据库更新失败时本轮上下文、历史和引用全部回滚。
- `history_messages` 保存所有成功原始问答，且不受压缩影响。
- `referenced_file_contents` 超过 10 轮后仍完整保存。
- GET 会话详情返回完整历史，不返回摘要。
- 迁移可以复制现有可识别消息。
- 损坏消息当前返回加载失败，不执行自动修复。
- `clear()` 后 `messages` 和 `history_messages` 均为空。
- 单 JVM 内同一会话并发请求不会互相覆盖。

## 明确采用的默认值

```yaml
chat:
  context:
    max-input-tokens: 256000
    safe-input-ratio: 0.95
    compression-trigger-ratio: 0.80
    compression-target-max-ratio: 0.20
    preserve-recent-rounds: 1
    max-summary-tokens: 4096
```

其中 `256,000` 是应用侧硬上限，`243,200` 是考虑约 5% 估算误差后的实际请求前安全上限。
